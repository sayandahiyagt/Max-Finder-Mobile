# Architecture assessment and proposed refactoring

The baseline assessment was recorded on 2026-10-31 against commit `7d68a94`. Refactoring work now proceeds under the user's instruction to improve the implementation while preserving current client-facing features. The original comparison remains historical; current decisions and progress are recorded below.

The documented layered modular monolith is the right foundation. The implementation contains useful UI and integration work, but its persistence model and authorization boundaries do not meet that design. Moving the existing functions into new folders would leave the main problems intact. The refactoring needs one data model, explicit application authorization, and smaller functions that each own a coherent operation.

Keep the useful implementation patterns. Improve the specification where operational details are missing. Do not turn every domain noun into a class, service, interface, and wrapper.

## Scope and evidence

The review covers every tracked application TypeScript file, the tests, CSS, SQL migrations, Supabase configuration, project configuration, CI, README, agent instructions, and the specification set under `docs/`. The lockfile was installed and its dependency graph audited. Dependency source code was not exhaustively reviewed.

At baseline, the inventory listed 45 application TypeScript files, 12 SQL migrations, five test files, 13 application files calling tables directly, and 19 importing Supabase helpers or packages. The linked [generated inventory](architecture-inventory.md) is regenerated from the current worktree and now lists 108 application TypeScript files, 23 migrations, 54 test files, and 17 files with explicit Supabase helper/package imports; application table access now goes through Prisma repositories rather than direct Supabase Data API calls. These counts describe coupling, not defects by themselves.

Two local scripts make parts of the review reproducible:

```bash
node scripts/assess-repository.mjs --write
node scripts/probe-architecture.mjs
```

The inventory is a source scan. The probes execute selected real functions with dummy input and provider stubs. Neither script reads environment files, contacts application services, or executes database commands. The architecture probe is a lightweight boundary smoke check; focused Jest tests remain the maintained regression suite.

No hosted schema, RLS behavior, Auth configuration, Storage objects, Vercel configuration, or real data was inspected. Repository SQL is evidence of intended deployment behavior, not proof of the current hosted state. No UI was driven in a browser during this assessment. Accessibility and appearance remain source-level findings; local HTTP smoke now covers refresh after a session cookie's stored expiry is forced into the past, while cryptographic JWT expiry remains unverified.

## Findings that determine the refactoring order

### A1. Hosted migration compatibility remains unproven

Priority: before any hosted migration or deployment.

The October 7 migrations create pets with an `id`, an Auth-user owner, inline `image_path`, required `age`, and lowercase species. They create pet-linked reports, conversations with `finder_id`, and messages with required `body`. The October 15 [initial migration](../supabase/migrations/202610150001_initial_maxfinder.sql) declares overlapping tables with `IF NOT EXISTS`, adds `profiles`, denormalized report fields, a spotting entity, `participant_id`, and message `content`.

`IF NOT EXISTS` preserves earlier table definitions. It does not reconcile their keys, constraints, defaults, or foreign-key targets. Later actions write both `body` and `content`, both conversation report IDs, and multiple participant columns. The former report action probed whether `pets` existed to select a schema path; the current [report action](../src/app/lost-pets/actions.ts) delegates to owned Pet Profile creation. The [reunion formatter](../src/features/reunions/formatting.ts) assembles several possible legacy row shapes at runtime.

Earlier RLS policies also remain unless explicitly dropped by name. Adding a stricter permissive policy does not cancel a broader existing permissive policy. The policy set needs review as a whole.

The eleven later alignment migrations and current Prisma schema now establish the documented application-user, Pet Profile image, report, conversation, and message shape. All 23 migrations replay on a clean isolated local stack, and schema assertions cover removed duplicate fields. A separate guarded upgrade test inserts synthetic rows at the legacy migration point, applies the eleven alignment migrations, and verifies ownership mapping, pet-image transfer, report states/contact data, canonical participants, and message content/read state survive. This does not prove either hosted project's migration history or real data compatibility; some legacy rows may still require repair. The organization directory remains specified but is not part of the current shipped implementation. Never rewrite an applied history or use a hosted reset to reconcile differences.

### Feature-preservation additions missing from the original model

The current Pet Profile UI and schema require an integer `age` and also support an optional `date_of_birth`; the baseline [data model](data-model.md) lists only `date_of_birth`. The shipped Spotting flow and `public.spottings` table are also absent from that relational model, despite being documented in the user flows and implemented in the app. For this refactor, preserve the current Pet Profile fields, anonymous Spotting creation/details, its image path, and public map pins. Treat any future schema simplification or visibility change as a product decision, not architectural cleanup.

### A2. Public exposure must be reviewed against hosted provider settings

Priority: before enabling shared environments.

[Map GET](../src/app/api/map/route.ts) and [report detail](../src/app/lost-pets/reports/[id]/page.tsx) preserve the shipped public browse experience. Activity, species, breed, time, and radius filters now run in Search on the server. The home map links directly to report details, and anonymous visitors can also open spotting details. Anonymous response projections omit contact choices; local integration tests deny anonymous direct table reads and private Pet Profile image reads through Supabase Data API.

Keep protected operations actor-scoped and public projections narrow. Hosted Data API, Storage, and RLS configuration remains uninspected under the local-only constraint, so local denial tests do not establish hosted exposure. Exact coordinates on existing public recovery map/detail pins are approved; public aggregate statistics and reunion details still need an exposure contract.

Public landing content can remain public. The team must decide what aggregate statistics and reunion details, if any, it may expose.

### A3. The Prisma and RLS contract still needs an explicit role

Priority: before any hosted connection or deployment.

The baseline had no application participant check for message sending, and its report mutation used a direct owner column. Those gaps are now fixed: the Communication repository scopes message creation to an active conversation participant, Lost Pet Report mutations follow ownership through the associated Pet Profile, and local database tests prove wrong-user and post-resolution message sends fail. The upload helper returns a storage path rather than a privileged client.

The unresolved security issue is how the Prisma connection interacts with RLS. A direct connection does not automatically carry the browser's Supabase JWT into PostgreSQL. Table owners and roles with `BYPASSRLS` may bypass policies. The local app currently performs domain authorization, but RLS tests through Supabase Data API do not prove that RLS protects Prisma queries.

A read-only audit of the guarded local database confirmed the current Prisma role is `postgres`, has `BYPASSRLS`, and sees `auth.uid()` as null. This is local-only evidence; it does not establish the role or grants configured in either hosted project.

Before hosted use, specify the application database role, its grants, whether request identity is propagated into PostgreSQL, and which defense-in-depth guarantees apply. Do not assume `auth.uid()` policies protect a Prisma query that lacks JWT claims. See the [Supabase Prisma guide](https://supabase.com/docs/guides/database/prisma) and [RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

### A4. Location defaults can become asserted facts

Priority: location privacy and deployment configuration.

The original default/device-coordinate submission issue is fixed. [LocationPickerFields](../src/components/location-picker.tsx) now begins without a selected point; a user must click or drag the map marker or explicitly request device location. Report and Spotting actions reject absent and out-of-range coordinates before persistence. Reverse-geocode responses use request sequencing so an older response cannot replace the selected point's label. The old `SpottingAdditionalInfo` component and its duplicate coordinate state were removed.

The user approved exact stored coordinates on current public recovery map and report-detail pins. The form also offers map selection when device location is unavailable; it does not provide typed address entry. The NYC fallback map center and Atlanta FAQ directory still need a single deployment-community decision.

### A5. Search result completeness needs an explicit contract

Priority: before imposing a public result cap.

Canonical activity, species, breed, time, and radius filtering now runs in the Search repository. Radius search expands its database bounds beyond the visible map viewport, then applies exact distance filtering; local database tests cover both behaviors. Both map entry points now share one UI filter default. The public API rejects missing viewport bounds instead of querying the entire database; explicit broad viewport queries still need the result-continuation contract. The map keeps its existing client interaction and pin selection.

The remaining issue is result volume: the public map query has no pagination or truncation metadata and may read every matching row in broad bounds. Adding a cap without a user-visible continuation state would silently hide pins. Define the result-continuation behavior before bounding results. Each pin now carries one canonical ISO timestamp, which the client formats in the viewer's locale; the duplicate server-local display string has been removed. Keep the existing loading, empty, and provider-failure states distinct.

### A6. Cross-service media cleanup needs an operational policy

Priority: reliability after persistence succeeds.

The old report action mixed Pet Profile and report creation, selected behavior by probing schema shape, invented pet attributes, copied account email into report contact data, and physically deleted reports. Those paths have been replaced: Pet Management owns Pet Profile and image writes, report creation accepts an existing owned pet and explicit contact choice, and removal changes lifecycle status. The runtime schema fallback and report-specific image upload are gone.

PostgreSQL changes and Storage operations cannot share a transaction. Pet Management and Spotting Management now own upload compensation and post-write cleanup through narrow Storage interfaces; Next.js actions handle form parsing and user feedback. Storage removal failures emit server diagnostics without logging object paths. An unchanged Pet Profile image is retained during text-only edits. The approved policy keeps `npm run db:media-audit` read-only and manually reviewed; it reports unreferenced candidates without modifying data. Do not add automatic object deletion or a durable cleanup queue in this refactor, and do not claim cross-service operations are atomic.

### A7. Auth lifecycle behavior is only partly verified

Priority: before relying on shared-environment sessions.

Validated identity lookup, browser session observation, server-action sign-out, and a Next.js 16 proxy that refreshes Auth claims and forwards updated cookies are now present. Local integration tests exercise synthetic account signup, application-user linkage and default `USER` role, password sign-in, explicit refresh-token rotation, and sign-out. The local Auth smoke also forces a valid session cookie's stored expiry into the past, verifies the Next proxy refreshes it, and reuses the returned cookies successfully. Separate tests confirm a provider-rejected expired session and a corrupted session cookie are treated as anonymous. This does not simulate a cryptographically expired JWT or a hosted email-confirmation callback. Local Auth has email confirmations disabled, and the hosted confirmation setting remains unverified. The future mobile client also needs an authenticated transport contract; server actions and browser cookies alone do not define one.

### A8. Readability problems are concentrated and fixable

Priority: alongside each module migration, after behavior is protected.

At baseline, profile, messaging, FAQ, report, spotting, home, and global CSS files compressed many declarations and markup onto long lines. A formatting-only pass has since normalized the tracked app, test, and local script sources. The homepage CSS module no longer contains unreferenced selectors, and unused global conversation-list and row-action styles were removed. The remaining global selectors without source literals are Leaflet hooks supplied by the map library. Five unused Next.js starter SVGs were removed after a repository-wide reference scan.

The app, tests, and local scripts are formatted. The report-creation action is named `createLostPetReport`, feature-specific matching and reunion logic live under `features/`, and species-dependent breed choices use controlled component state rather than DOM queries. Keep extracting components when they express a visible unit or isolate state; do not split files just to shorten them. The remaining `lib/` modules are shared utilities and provider integrations.

Keep the dynamic map wrappers because they isolate the browser-only Leaflet dependency. The redundant Spotting location wrapper and unused map callback props have been removed after usage checks. Small files are not automatically unnecessary abstractions.

Keep CSS modules and existing root variables. Consolidate repeated values into the current theme rather than introducing a new visual system. The global stylesheet keeps Arial as the active font; unused Geist font loading has been removed from the root layout. The conversation wrapper no longer reserves an empty desktop grid column. The shared app header, sign-in/sign-up surfaces, location picker, and report-detail map now keep their styles beside their owners; account-form rules are reused by profile editing, and Leaflet marker styles travel with their map component. General action errors retain a clearly named global style. Verify responsive pages and keyboard focus after cleanup.

### A9. Errors and external requests need narrower ownership

Priority: application boundary and integration migrations.

Unexpected page failures now show a generic, accessible retry path without rendering provider or database error details, and missing pages/records have a direct route back to the map. Home statistics show explicit loading and query-failure states while leaving the map and other home content available. Pet Profile create/edit/delete, Lost Pet Report create/update/removal, and Spotting creation actions now return safe inline errors; forms retain entered values and selected locations, while Spotting asks for the image again after an error. Report update/removal checks affected-row results, invalid normal-edit status values are rejected, API boundaries return explicit 400/503 responses, and Storage cleanup failures emit server-side diagnostics without object paths. Use typed form results where they clarify expected caller behavior; do not wrap every repository operation.

At baseline, map and detail reads reverse-geocoded placeholder labels, and Map GET could fan out one provider request per result. Read-time repair has since been removed: map and detail views use the stored label or display `Address unavailable` for legacy placeholders. Report and Spotting write flows still persist a usable label, and the reverse-geocoding endpoint remains for explicit pin selection. This avoids outbound work during reads while keeping current entry flows. Any legacy data repair must be planned before a hosted migration; provider capacity and location privacy still need a documented shared-deployment contract.

### A10. Conversation invariants need one owner

Priority: communication migration.

Keep two distinct participants, report-scoped uniqueness, and private history. After the report becomes `FOUND` or `REMOVED`, participants retain read access to the conversation but cannot send new messages. Concurrent create-or-get requests can both miss the initial read and collide on insertion. The repository treats the unique constraint as the authority and retrieves the winning row after a recognized conflict; a local database test now invokes the operation concurrently and verifies both callers receive the same conversation.

At baseline, the list sorted by conversation `updated_at`, while sending a message only inserted a message. The list now derives its display/sort timestamp from each conversation's latest message; a local database regression makes `updated_at` stale to prove the behavior. The application does not call the schema read-state RPC; message read receipts are not exposed in the current thread UI. Participant display names now come from Prisma relations, so the legacy participant-name RPC is also unused. The final RLS migration and application repository both enforce the approved read-only-after-resolution contract; local tests verify participants can still read history but cannot send after either `FOUND` or `REMOVED`.

Priority: before declaring the refactor ready for review.

At baseline, the 17 tests covered configuration, display-name validation, reunion formatting, two matching scenarios, and one geocoding route case. The current suite has 207 unit tests plus 7 local database tests, including synthetic Auth signup/sign-in/refresh/sign-out and default-role enforcement, generic authentication errors and session cleanup after profile failures, anonymous/wrong-user/nonparticipant checks, identity linkage, migration-shape assertions, anonymous report contact omission with nonempty synthetic contact data, legacy location-label handling, media upload/cleanup behavior, concurrent conversation creation, resolved conversation history and blocked sends after `FOUND`/`REMOVED`, authenticated-boundary redirects, distinct anonymous/missing-profile identity responses, invalid species/size/weight/contact rejection before external writes, map request parsing and missing-bounds rejection, map UI filter/radius query encoding and Spotting detail-link rendering, map-pin links, species-dependent filter behavior, local date/time and offset handling, typed location-search response parsing, shared map activity/time/radius filters, shared form text normalization and rejection of non-text values, safe error and not-found rendering, community-stat success/loading/failure states, Pet Profile inline action errors and retained form values, Lost Pet Report inline errors and retained values, selected location/date restoration, normal status transitions, safe update/removal failures, anonymous Spotting inline failures and retained values, message text trimming and rejection of file or overlong values, Storage compensation after failed writes and retention of unchanged Pet Profile images, consistent placeholder-label parsing, Pet Profile deletion success, report-reference, wrong-owner, and missing-profile handling, reunion assembly, image-storage failure handling, consolidated map failure-count handling, and loopback-only test-environment validation. Priority: before considering the refactoring ready for wider use.

The current `npm audit` reports six low findings in the development toolchain, all through Jest configuration and its `deepmerge` dependency. The registry has no fixed `deepmerge` release; npm's suggested Jest downgrade would be a major downgrade. Overrides now pin `glob` 14.0.3 and `minimatch` 11.0.3, removing all 32 moderate findings without changing the direct tool versions. `npm audit --omit=dev` reports no production advisories. ## Where the specification itself needs improvement

These are proposed decisions for team review, not silently adopted requirements:

1. **One migration authority.** Prefer Supabase SQL migrations for this run because the repository already has SQL policies, functions, Auth, and Storage setup, and the user prefers CLI migrations. Use Prisma for typed application queries and model generation. Disable the competing Prisma Migrate workflow explicitly if approved. A local-only CLI workflow must be documented before the hosted one.
2. **A concrete Prisma and RLS contract.** Specify database role privileges, request identity propagation where used, and which defense-in-depth guarantees actually apply. Do not promise RLS protection that the chosen connection bypasses.
3. **A reusable application interface.** Framework-independent functions accept validated input and authenticated application identity. Web actions, server rendering, and JSON handlers call those functions in-process. Add mobile-facing JSON endpoints as required, not speculative endpoint copies for every action today.
4. **Operation atomicity.** Define idempotent profile linkage, unique conversation conflict handling, database transactions, and recovery for Auth/Storage partial failures. PostgreSQL transactions cannot roll back an uploaded object or an Auth account.
5. **State transitions and deletion.** Existing conversations stay readable and become read-only after FOUND or REMOVED. Who can reopen FOUND, what REMOVED permits, and the physical account-deletion order still need definition. Do not invent retention periods.
6. **Privacy and visibility.** Exact coordinates on existing public recovery map/detail pins are approved. Public aggregate statistics and reunion details still need an exposure decision. Account email must not become an implicit report contact choice.
7. **Scope and acceptance examples.** Document the existing spotting and reunion behavior, weight ranges versus size, supported species, locality defaults, and read receipts. Preserve current client-facing features until a product decision changes them. Keep matching deterministic, with accepted ranking examples rather than unexplained weights alone.
8. **Operational acceptance.** Define pagination, error semantics, retry behavior, local seeding, environment rejection checks, and the minimum browser journeys. Define the same application behavior across web entry points without requiring an extra network hop during server rendering.

Separate internal application user IDs from Auth IDs as documented. The extra identity mapping is justified by application ownership and future provider independence, but it needs reliable creation, uniqueness, deletion, and reconciliation behavior. Do not add generic identity abstractions beyond those needs.

## Proposed structure

This is a file-ownership proposal, not a mandate to create empty modules or one file for every operation:

```text
src/
  app/                         Next.js pages, route handlers, actions, layouts
  features/
    identity/                  Application profile and role operations
    pets/                      Pet ownership and media coordination
    lost-pet-reports/          Report input, lifecycle, contact choices
    search/                    Filtering, candidate selection, pure ranking
    communication/             Conversations and messages
    organizations/             Database-owned directory
    administration/            Privileged orchestration and CSV
  server/
    auth/                      Supabase session validation and actor creation
    database/                  Prisma client and repository implementations
    media/                     Supabase Storage adapter
    geocoding/                 Provider adapter
  components/                  Shared presentation only
prisma/                        Prisma models and configuration
supabase/
  migrations/                  Sole SQL history, if approved
tests/
  integration/                 Isolated local database and adapter tests
  browser/                     Dummy-data user journeys
```

Keep feature-specific UI beside its feature when that improves navigation. Small pure helpers and tests may be colocated. A feature's public application functions define its boundary; do not introduce separate controller, manager, service, use-case, and facade layers for the same operation. Add an interface when there is a real substitution need, such as local/test media versus hosted media. No dependency-injection container is required.

Database and privileged provider modules must be server-only. Feature rules must not import Next.js, React, or Supabase. Cross-feature calls should use the owning feature's public functions. Enforce those directions with targeted lint rules after the file convention is approved.
